A **Telegram bot** that tracks orders on a supplier's platform, written because checking order status meant logging into a web app several times a day to look at a list that rarely changed.

The design constraint was staying a polite client of an API that isn't mine. Rather than polling on a schedule, the bot is **manual-refresh by default**: `/active`, `/recent` and `/order <po>` all answer from a local cache with no network call at all, and only `/refresh` reaches out – behind a cooldown, a cache TTL, and a hard daily call cap. Auth tokens refresh on expiry, with exactly one retry on a 401 or 403, and if authentication fails the bot keeps serving cache rather than going dark.

Built with **TypeScript** on **Node.js** using **grammY** for the bot, **SQLite** (`better-sqlite3`) for the cache and order history, and **Zod** for validating both the environment config and the API responses. It ships as a **Docker** container and runs on a home NAS, with `/health` and `/last-sync` endpoints so it can be monitored like anything else. Access is restricted to an allow-list of chat ids – a Telegram bot is a public endpoint by default, and the interesting half of the threat model is people who simply find it.
